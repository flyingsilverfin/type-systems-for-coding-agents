Do types make weak agents better?

The same codebase in Rust and Python: toydb, a distributed SQL database, at growing sizes (tiers 1–4). Agents of different strength get identical tasks; a compiler (or not) plus a few visible tests are their only validators; held-back tests decide correctness.

Where it stands

  • Tier 4 (12.5k lines of Rust, 7 more extension layers, identical docs in both languages): the type system no longer decides anything for any model. After a post-run audit of the hidden tests, 20 of 108 runs pass: Haiku Rust 2/18 vs Python 1/18, Sonnet 3/18 vs 2/18, Opus 8/18 vs 4/18 (p ≈ 0.29). Nearly every failure is at a site no type checks, and it fails in both languages: lint rules applied through BETWEEN/IN and simple-CASE expansions (0 of 36 runs), DESCRIBE typing of date arithmetic (1 of 18), the ALTER view-dependency check, BETWEEN/IN and NOT LIKE rewritten in the parser. Python agents reached the sites Rust's compiler names: only 1 of 54 Python runs crashed at an unhandled variant (Haiku at tier 3: 6 of 18). The codebase is consistent enough that grepping for a sibling variant finds the same list the compiler gives. Rust's forced arms again came with wrong content, e.g. DATE written as a plain JSON string: Rust right in 3 of 9 runs, Python 9 of 9, through its generic fallback. Reading: at scale, the bottleneck is the semantic rules, not finding the sites, and types only help with finding the sites.
  • Experiment 1 across three models: the compiler's advantage is a weak-model effect. With the README's extension docs removed (code unchanged), 3 repeats × 6 tasks per cell: Haiku Rust 10/18 vs Python 5/18, and 6 of 18 Python runs missed a site Rust's compiler flags (Rust 0, p ≈ 0.02). Sonnet 11/18 vs 12/18, and Opus 18/18 vs 13/18: neither missed a single compiler-flagged site in Python (0 of 36). Sonnet and Opus found the JSON writers and the hand-written serialization on their own. Their Python failures are all at sites no type checks (BETWEEN/IN kept as a parser expansion, the optional COLUMN in ALTER digests). The ALTER one is partly a documentation confound: the Rust digest module states "optional words are left out" as a rule, while the Python docstring only implies it. Meanwhile exhaustive matching cut the other way for Rust: 5 Rust runs (Haiku 2, Sonnet 3) added the forced arm with the wrong content, e.g. a JSON import arm for DATE that reads a plain string, where Python's generic fallback handled the typed form automatically. Reading: types tell you where, not what. That matters for a weak agent that can't find the where on its own, and stops mattering once the agent can.
  • Tier 3: types tell you where, not what. I added four extension layers to toydb (JSON output, statement digests, column statistics, export/import) that consume the core types, so each feature task has to reach code far from where the feature lives. Transplant (tier-2 solutions dropped onto tier 3 unchanged): in Rust, 10 of 12 feature solutions fail to compile, and every error names a missing extension site. In Python, 6 of 12 fail the agent's own visible script (a crash or wrong answers), but 4 (DATE, release) pass the visible script and the entire existing suite while failing every extension script. The remaining 2 per language (BETWEEN/IN) are silent in both. Real agents on tier 3 didn't need the compiler for this: Python agents reached every site Rust's compiler would have flagged, in 12 of 12 feature runs (the README's Extensions section names them). Of the 7 failures (Rust 3, Python 4, all escaped with a green check.sh), every one is at a site no type system in either language checks: digest text, JSON member lists, statistics upkeep, and whether BETWEEN stays in the AST.
  • First spread, at tier 2, and it says something about where types help. 2 of the 5 tier-1 Haiku Python solutions to the feature tasks (CASE, DATE) pass every tier-1 test and the whole tier-2 suite when applied unchanged to the full codebase, then crash on the cluster wire (UnexpectedEof). Python's hand-written serialization was skipped or incomplete. At tier 1 nothing uses it, so it looks like dead code. Rust: 0 such failures of 10, because serde is derived. Python Opus: 0 of 5. Agents working on the full codebase got it right in Python too, 12 of 12 with or without a hint: there the README and the code show that values and plans cross the network. Reading: types (here, derived serialization) protect weak agents when the code that consumes a change is out of their view. That is what tier 3 is built to test.
  • Tier 1 (toydb SQL core, about 6k lines) still shows no spread: 27 of 28 runs pass. The one failure is Haiku in Python on DISTINCT, an escaped defect: COUNT(DISTINCT) gives the argument-count error instead of the parse error the spec gives twice. Rust costs Haiku about 12% more output tokens (geometric mean over tasks) and Opus nothing; turns are level. Compile time is negligible: 59–62 s of Rust builds across 7 tasks against roughly 2,000–2,400 s of wall time.

Design

  • Subject: toydb (Erik Grinaker, Apache-2.0) and a structurally parallel Python port that passes the same golden scripts byte for byte. Each tier is a larger slice of it: SQL core (tier 1), full toydb with Raft (tier 2), and extension layers that consume the core types (tiers 3–4).
  • Arms: Rust (compiler + one visible golden script + check.sh) vs Python (the same visible script + check.sh, no type checker).
  • Agents: Claude Code subagents with a fixed prompt: Haiku · low, Sonnet · medium and Opus · high.
  • Correctness: hidden golden scripts (SQL and end-to-end cluster scripts), compared byte for byte, plus the full regression suite (every existing golden script and unit test).
  • Oracle: an author writes each task's spec and hidden scripts; two independent reference implementations, one per language, must agree byte for byte, and a reconciler settles every disagreement against the spec.

Isolation & integrity

  • Each run gets its own workspace: the tier's codebase, TASK.md, one visible golden script and check.sh.
  • The prompt forbids reading outside the workspace, using the web and spawning subagents. Every Bash/Read/Grep path in each transcript is audited afterwards.
  • Hidden scripts, reference solutions and other runs' workspaces are chmod 000 while agents run.
  • The Rust build is pre-warmed, so the agent never pays the cold dependency build.
  • Hidden scripts are copied into the workspace only at grading time, and the task directories are restored afterwards.

Metrics

  • Pass: build OK, every hidden golden script matches byte for byte, and the full regression suite stays green.
  • Escaped defects: last visible check green but hidden tests fail. This is the headline number for the talk.
  • Effort: turns, tool calls, output/thinking tokens and input tokens incl. cache, all from subagent transcripts (deduplicated per API message).
  • Time: total wall time, plus time inside check.sh split into build and tests (logged by check.sh itself), so time excluding compile is exact.
  • Validator signal: how many check.sh runs, and how many failed at compile vs failed visible tests.

Tier 2 · full toydb with Raft, server, client (about 8.5k lines Rust / 11.3k Python)

  • Setup: the same 7 tasks and 28 cells on the full codebase. Hidden tests are the tier-1 SQL scripts plus 3–4 cluster scripts per task (real 3–5 node clusters, several clients). TASK.md says that cluster scripts are among the hidden tests.
  • Correctness: 28/28 pass, every cluster script included. 20 of 28 agents wrote a cluster script of their own; the hint invited this.

Tier 3 · toydb plus four extension layers (about 10k lines Rust / 12.7k Python)

  • Setup. Tier 2 plus four extension layers, about 1.5k lines each in Rust and Python, written to one language-neutral spec by independent agents and reconciled to byte-identical output on 32 extension scripts. Each extension follows generic rules: plan JSON is derived from the display, digests are canonical SQL with literals as ?, statistics follow their columns, and import goes through INSERT. So the correct output for a new construct follows from the spec without naming it. Python follows the port's case _: panic convention, so a missed arm fails loudly at run time rather than silently.
  • Hidden scripts: each task's tier-1 and tier-2 scripts, plus 5–6 new extension scripts (SQL and cluster) per feature task that drive the feature through the extensions. TASK.md is the same as at tier 2 and doesn't mention the extensions; agents learn about them only from the README.
  • Result: Rust 11/14, Python 10/14 (Haiku 5/7 vs 4/7, Opus 6/7 vs 6/7). All 7 failures passed the agent's own last check.sh. Per task:
  • · between_in (Rust Opus, Python Haiku): BETWEEN/IN still expanded in the parser, as at tiers 1–2, so SHOW STATEMENTS shows v >= ? AND v <= ? and merges it with the hand-written expansion. Rust Haiku and Python Opus kept the constructs in the AST. Neither type system can force this.
  • · alter (Rust Haiku, both Python): the digest keeps the optional COLUMN (ADD COLUMN x), although EXT_SPEC §3.2 says optional words are left out, including for statements added later. Rust Haiku also didn't move or drop column statistics on RENAME/DROP. The compiler forces a digest arm but not its text.
  • · release (Rust Haiku): NOT LIKE is lowered in the parser, so its digest reads NOT s LIKE ?. Silent in both languages.
  • · distinct (Python Haiku): the JSON for the Distinct node carries an extra width member; the spec says nodes carry only what their display line shows. A Rust agent could make the same mistake.
  • Cost: Rust Haiku used 23% more output tokens than Python Haiku (573k vs 465k over 7 tasks) and about 18% more wall time. For Opus the two are level (236k vs 241k tokens). Compile time totalled 162–221 s per setting, against 590–620 s of Python test time; the Python suite is about 1.6× slower here.

Would the tier-2 solutions have survived at tier 3?

  • Each tier-2 run's final changes were applied to a fresh tier-3 base by a per-file three-way merge. 21 of 28 had textual conflicts (adjacent keyword-list entries, keyword-count tests, enum variant numbers). Opus agents resolved them under a rule to keep both sides and add nothing, without building or testing. A script checked that every edit stayed inside a conflict region or was a permitted renumbering. I fixed three resolution errors by hand: two keyword counts were one short, and in the date runs the run's DEFAULT-literal rendering was moved into the display closure, as the reference port does.
  • Rust: 10 of 12 feature solutions don't build. Every error is a non-exhaustive match or missing field at an extension site, so the compiler lists the work. The two that build are BETWEEN/IN, which then fail all 6 extension scripts silently.
  • Python: 6 of 12 fail the visible script, so an agent would notice: CASE and ALTER crash in the digest printer, and DISTINCT loses its flag in the AST rewrite. 4 of 12 (DATE, release) pass the visible script and the whole existing suite, then fail all 6 extension scripts. 2 (BETWEEN/IN) are silent as in Rust. Bugfix carries over in both languages (4/4).
  • So, counting what the agent's own check.sh would flag: Rust 10/12, Python 6/12. This is the same pattern as the tier-1→2 transplant, now on six tasks instead of two: when the consumers of a change are out of the agent's view, Rust's compiler finds them and Python's tests often don't. The real tier-3 runs show the other half: given a README that names the consumers, the weak Python agent found them anyway.

Scale-up plan

  • Reference codebase: toydb (Erik Grinaker, Apache-2.0). A distributed SQL database in Rust: lexer/parser, planner with 5 optimizers, executor, MVCC transactions, bitcask/memory storage, key encoding, Raft. It is about 7.9k lines of non-test code (+3.8k inline tests) and ships 107 golden test scripts for SQL and storage, with about 10k lines of expected output in a language-neutral command → output format, including 428 exact error messages and printed plan trees.
  • Port direction: Rust → Python. The Rust original is the trusted reference, and its golden scripts become the acceptance test for the Python port: a Python goldenscript runner plus ports of toydb's test runners. A port that passes all 107 scripts byte for byte is behaviourally equivalent, which avoids the problem of having to trust AI-written Python.
  • Tier 1 (done, 2026-11-17: 27/28 pass): toydb SQL core in-process: parser, types, planner/optimizer, executor, local engine, MVCC, storage, encoding. About 6.2k lines of Rust application code against 7.8k lines in the Python port. A pipeline of 7 Fable 5.2 agents built the port in 57 minutes (1.29M tokens). It passes 130/130 golden-script runs byte for byte (93 SQL plus 37 storage) and 117 unit tests, which I re-checked myself. An independent Fable reviewer found it faithful with no cheating; the issues it raised were minor, e.g. the sorted-list BTreeMap is O(n) per insert.
  • Tier 2 (done, 2026-11-18: 28/28 pass; transplant test shows 2 silent Python Haiku failures): full toydb, adding Raft consensus, the Raft SQL engine, server/client, bins and the end-to-end cluster tests. About 8.5k lines of Rust and 11.3k of Python application code.
  • Tier 3 (done, 2026-11-19: Rust 11/14, Python 10/14; every failure at a site no type checks; transplant: Rust's compiler flags 10/12 tier-2 solutions, Python's own checks 6/12): tier 2 plus four extension layers, JSON output, statement digests, column statistics, export/import, about 1.5k lines per language. The extensions are consumers of the core types (Value, DataType, plan nodes, AST, catalog), so the same tasks must also reach code far from the SQL core.
  • The same 7 tasks at every tier, so only the codebase size changes:
    • between_in, a local control.
    • case, which touches expression traversal, aggregates and folding.
    • date, a new type that touches every match on Value/DataType and the order of the key encoding.
    • distinct, including DISTINCT aggregates.
    • alter: ADD, DROP and RENAME COLUMN, which need backfill and index re-keying, and Raft catalog writes at tier 2.
    • release: six small changes in six areas.
    • bugfix: four injected logic bugs, as a control.
  • Oracle for the new tasks: a Fable 5.2 / Opus 5.5 author writes the SPEC, a visible script and 8–12 hidden golden scripts. Two independent Fable 5.2 implementers, one per language, see only the SPEC and the visible script.
