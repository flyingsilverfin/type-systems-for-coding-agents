# Type systems for coding agents

Do static types help AI coding agents? This repo holds an experiment that gives Rust and Python
versions of the same codebase to agents of different strength (Claude Haiku, Sonnet and Opus). Each
agent gets an identical task, and its only feedback is a retry loop of a compiler (or none), a few
visible tests and `./check.sh`. Held-back tests decide correctness. It was built for a Rust meetup talk.

## Findings so far

**Types tell you *where*, not *what*.**

- **Small and medium codebases (tier 0, toydb tiers 1–2): no difference.** Agents in both languages
  pass almost everything. Rust costs somewhat more time and tokens.
- **Code that consumes a change is out of view.** A *transplant* test applies each agent's solution
  unchanged to the next-larger tier. In Python it often passes every test the agent could run, then
  fails at code the agent never saw: hand-written serialization at tier 2, JSON writers and import
  parsing at tier 3. In Rust, a non-exhaustive match or a derived impl flags or covers those sites
  instead:
  - Tier 1 → 2: Python 2/5 silent failures, Rust 0/10.
  - Tier 2 → 3: Rust's compiler flags 10/12 solutions, Python's own checks only 6/12.
- **Experiment 1: tier 3 without the README's description of the extensions.** 6 feature tasks ×
  3 repeats × 3 models (108 runs):

  | Model | Rust pass | Python pass | Python missed a site the Rust compiler flags |
  |---|---|---|---|
  | Haiku · low | 10/18 | 5/18 | 6/18 (Rust 0/18, p ≈ 0.02) |
  | Sonnet · medium | 11/18 | 12/18 | 0/18 |
  | Opus · high | 18/18 | 13/18 | 0/18 |

  The compiler rescued the weak model when nothing else pointed at the affected code. Sonnet and Opus
  found that code on their own. All of their remaining failures, in both languages, are content no
  type system checks: digest text, parser expansions, statistics upkeep. Exhaustive matching also has
  a cost: weaker Rust agents sometimes filled a forced arm with the wrong content, where Python's
  generic fallback was right automatically. Opus's 18 vs 13 is mostly a documentation confound (see
  `analysis/notes.json`); tier 4 enforces identical docs.
- **Tier 4: seven more extension layers** (views, FORMAT, DESCRIBE, ESTIMATE, prepared statements, LINT,
  change log). Rust has 12.5k lines of application code and Python 14.9k, and both languages use identical
  doc comments. The setup is experiment 1's: the README has no extension docs, 108 runs. After a post-run
  audit of the hidden tests (described in the report; the audit log is held back with the tests):

  | Model | Rust pass | Python pass | Python crashed at an unhandled variant |
  |---|---|---|---|
  | Haiku · low | 2/18 | 1/18 | 0/18 |
  | Sonnet · medium | 3/18 | 2/18 | 1/18 |
  | Opus · high | 8/18 | 4/18 (p ≈ 0.29) | 0/18 |

  Python agents of every strength now reach the sites the Rust compiler names, because grepping for a sibling
  variant finds the same list. Nearly every failure, in both languages, is at a site no type checks:
  - lint rules applied through BETWEEN/IN and CASE expansions (0 of 36 runs got this);
  - DESCRIBE typing of date arithmetic;
  - the ALTER view-dependency check;
  - constructs rewritten in the parser.

  At this scale the bottleneck is the semantic rules, not finding the sites, and types only help with
  finding the sites. A tier 5 (20k+ lines) would test whether finding the sites gets hard again.

The full write-up, including per-run tables, is generated by `analysis/render.py` into
`artifact/index.html`. Open that file in a browser.

## Layout

| Path | What |
|---|---|

| `toydb/tiers/t1..t4/{rust,python}` | The benchmark codebases: t1 = SQL core in-process, t2 = full toydb (Raft, server, client, e2e cluster tests), t3 = t2 plus four extension layers (JSON output, statement digests, column statistics, export/import; spec in `toydb/tiers/t3/EXT_SPEC.md`), t4 = t3 plus seven more (spec in `toydb/tiers/t4/EXT4_SPEC.md`, module docs in `EXT4_DOCS.md`). Each has `check.sh`, `grade.py` and `LAYOUT.md` |
| `toydb/tasks/<task>/` | The 7 tasks (between_in, case, date, distinct, alter, release, bugfix): `SPEC.md` (+ tier addenda) and the visible golden script |
| `template*/`, `data*/`, `build_v2/` | Tier 0: a small library-lending CLI on TypeDB, in both languages, with visible datasets |
| `bench/` | Harness: workspace builders (`make_run*.py`), graders, run lists, the transplant scripts, the usage guard, and `bench/workflows/` (the scripts that orchestrated the build and run agents) |
| `analysis/` | `transcripts.py` (tokens, turns, timings and isolation audit from agent transcripts), `render.py` (the report), `notes.json` (findings) |
| `results/`, `meta/`, `logs/` | Per-run grades (JSON), workspace metadata, and per-`check.sh` timing logs |

## Method in brief

- **Isolation.** Every run gets a fresh workspace and may read only that. Hidden tests, reference
  solutions and other runs are locked (`chmod 000`) while agents run, and transcripts are audited
  for reads outside the workspace.
- **Oracle.** For every task, an author writes the spec and the hidden tests. Two independent
  implementations, one per language, must agree byte for byte, and a reconciler settles every
  disagreement against the spec.
- **Fairness.** Each language's code must be idiomatic: exhaustive matching where a careful Rust
  engineer would use it, and the Python port's own conventions. Nothing is added only to make a task
  fail or pass.
- **Metrics.** Correctness on hidden tests, plus escapes (the agent's own last `check.sh` was green
  but grading fails), output and input tokens, turns, and wall time split into compile, test and
  agent time.

## Reproducing

The harness was run from Claude Code workflows (`bench/workflows/`) with paths under
`/home/user/agentbench`. To grade a workspace, run `python3 toydb/tiers/<tier>/grade.py <lang> <ws> <scripts-dir>`.
The hidden tests and reference solutions are not in this repo yet (see `HELD_BACK.md`), so
end-to-end grading needs them.
